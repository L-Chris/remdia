# Blaze 在 remdia 上的实测（2026-10-28）

结论：保留为可选的本地构建实验，暂不替换 Cargo、发布构建或 CI。
Blaze 是 Rust 构建工具，不是媒体后端，不改变 remdia 不依赖 FFmpeg 的架构。
CLI 的小改动有收益，但完整 SDK 在本机触及内存预算，不能据此声称整个项目构建加速。

## 环境与版本

- Apple M6，12 核，16 GiB RAM，macOS 27.0，aarch64；接电的日常开发环境，其他应用保持运行。
- SDK：`d69ef6e72806c11a2f517a8fd65b6ba28c16ac87`，Git tree `4c69a31c43e6cc4592718a8618074070ece6356f`。
- Cargo stable / Rust `1.99.1 (58cf8f9c3 2026-10-13)`，LLVM 23.1.1。
- Blaze 发布包 `v0.20261027.0`，其 `--version` 实际为 `blaze 0.20261027.0 (49ca152)`。
- Blaze 自带 Rust `1.101.0-nightly (16d1ffac1 2026-10-26)`，LLVM 23.1.4。另设完全相同 nightly 的原生 Cargo 对照。
- 官方 ARM64 macOS 压缩包 SHA-256：`47dae8e838765931ed8e216a94e4d75454469fa6c3950d1c02eba2841bc8dad5`。
- 测试发布包默认 Cranelift 后端。2026-10-28 的上游 main 已有后续修改，本报告不代表这些未发布版本。

没有执行 `blaze enable`，没有修改全局 Cargo 配置、项目依赖、默认工具链或 replayer 的 SDK 引用。
Blaze 的可执行文件、独立 nightly、daemon home、缓存和构建目录均隔离在 `target/blaze-eval/`。

## 测量方法

原始逐轮数字和版本信息见 [JSON 数据](blaze-2026-10-28.json)。
脚本在独立 Git 源码副本上比较三个构建器，使用 `--locked --offline`、相同锁文件、相同 job 数、独立空 target 和缓存。
冷构建指本项目构建目录为空、daemon 未启动；Cargo registry、系统 SDK、Blaze 本身和自带 Rust 已提前准备，不清空 OS 文件缓存。
Blaze 的预编译标准库包可能在首次构建时联网下载，即使传了 Cargo 的 `--offline`；冷构建时间包含该过程，不能简单扣除下载耗时。

CLI 每种构建器测一次冷构建、5 次无修改构建、一次预热修改、5 次函数体修改，最后还原构建。
修改在 `main` 开头打印固定长度的日志字面量计数标记，逐次执行新产物 `--version`，断言输出确实更新；不能只看编译命令退出码。
这是非常小的日志修改，不代表类型变更、依赖变更、插件实现修改或 C bridge 修改。
增量/无修改数据取 5 次中位数，冷构建只有一次，不能视作跨机器统计结论。
完整 workspace 的单 job 冷构建单独比较，不与双 job 数据混算。

内存每 50 ms 采样进程树，加上独立 Blaze 安装目录启动的脱离父进程 daemon/worker。
同时记录 RSS 与 macOS physical footprint，后者能反映压缩内存；RSS 求和可能重复统计共享页。
二者均是采样峰值，不是精确的内核高水位。退出后 1 秒另采常驻内存。
仅对前台使用 `/usr/bin/time -l` 会漏掉 daemon，不能用它的几十 MiB 来代表 Blaze 总占用。
墙钟计时用阻塞 wait，避免 Python 带 timeout 的 wait 引入最高约 50 ms 轮询误差。

设置 `BLAZE_MEMORY_MAX=4G`、`BLAZE_SPARE=0`；上游内存参数是 worker 淘汰预算，并非硬上限。
采样器在 RSS 或 footprint 总计超过 6 GiB、全机 swap 增长超过 512 MiB、或者超时后终止本次命令及所属编译进程。
未终止其他应用。所有已测构建的 swap 均未增长。

## 构建时间与内存

CLI，单 job，dev profile：

| 指标 | Cargo stable | Cargo 同 nightly | Blaze |
|---|---:|---:|---:|
| 冷构建，秒 | 17.509 | 18.450 | 19.011 |
| 无修改中位数，ms | 44.4 | 33.8 | 127.4 |
| 日志修改中位数，ms | 254.9 | 244.4 | 159.8 |
| 冷构建峰值 RSS，MiB | 360 | 384 | 4,588 |
| 冷构建峰值 footprint，MiB | 236 | 251 | 4,470 |
| 末轮退出后 RSS，MiB | 0 | 0 | 2,897 |
| 末轮退出后 footprint，MiB | 0 | 0 | 2,825 |

Blaze 相对 stable 的这类增量构建耗时下降 **37.3%**，每次省 **95 ms**；相同 nightly 对照下下降 **34.6%**，省 **85 ms**。
冷构建没有提速，无修改构建约慢 2.9 倍；收益需要权衡数 GiB 常驻内存。
所有 5 次修改及预热修改均验证通过，日志含 `[blaze]`，没有把 Cargo 回退计入 Blaze 成绩。

完整 workspace，单 job，dev profile，各一次冷构建：

| 构建器 | 结果 | 墙钟，秒 | 峰值 RSS，MiB | 峰值 footprint，MiB |
|---|---|---:|---:|---:|
| Cargo stable | 成功 | 81.933 | 563 | 424 |
| Cargo 同 nightly | 成功 | 81.826 | 546 | 404 |
| Blaze | 超过 6 GiB 保护，终止 | 55.270（未完成） | 4,991 | 6,187 |

这里的单 job 是为控制内存而统一设置的 `CARGO_BUILD_JOBS=1` 和 `CMAKE_BUILD_PARALLEL_LEVEL=1`，并非日常默认并行度的构建速度。
Blaze 自身仍可能启动多个 worker；降低 Cargo job 数未能让完整 SDK 落入此内存预算。

完整 SDK 构建失败的耗时只是触发保护所需时间，不能算成功时间或计算加速比。
没有成功的 Blaze 全量插件产物，因此不声称 VideoToolbox bridge、native cdylib 或 replayer 的 Blaze 构建已通过验收。

另试 `blaze build -p remdia-cli --release --locked --offline`：命令成功，15.136 秒，峰值 RSS 3,810 MiB、footprint 3,611 MiB，`--version` 正常。
但固定版本的[支持文档](https://github.com/indexable-inc/blaze/blob/v0.20261027.0/docs/support.md)仍列出 LTO 限制，与命令成功不能等同。
未验证其是否保留本项目 `lto=true / codegen-units=1 / strip="symbols"` 的优化语义，因此这条数据只作命令兼容性记录，不作为等价 release 加速结论。

Blaze 另占独立工具 180.0 MiB、自带 nightly 659.8 MiB、函数/标准库缓存 318.2 MiB，连同本组 target 合计约 1.55 GiB。
59.7 MiB 下载压缩包还可单独删除；未计入上述合计。没有把下载耗时或额外工具链空间藏进 Cargo 的既有安装里。
该占用是本次单组 CLI 实验的状态，不是多次实验目录加总，也不代表缓存增长上限。

## 产物与媒体检查

独立测试了 Blaze CLI + Cargo 构建的原有 native/macOS 插件。这是混合构建验证，不能代替全 Blaze 插件的 ABI 验证。
对提交在仓库中的 `tests/fixtures/av.mp4`：

- probe 返回相同媒体信息；软件解码均为 142 个音频 frame、72 个视频 frame、EOF=true。
- PNG 缩略图、1 秒 WAV、1 秒 MP3 均成功，两种 CLI 的输出 SHA-256 分别完全相同。
- 测运行内存前已停止 Blaze daemon，编译器后台占用与媒体进程分开统计。
- 语料只有 3 秒、160×90，适合功能检查，不代表真实高清播放性能或长时间稳定性。

混合构建与 Cargo CLI 各解码 5 次，中位墙钟分别为 103.4 / 100.7 ms，采样峰值 RSS 为 27.5 / 25.1 MiB，footprint 为 7.34 / 7.28 MiB。
这种短任务下几 ms 的差异不足以声称运行性能改善，RSS 也可能漏掉短峰值；两者的 SDK 托管预算峰值同为 16,814,530 bytes。
Blaze 不会随正式应用分发；本次实验没有改变发布包大小。dev CLI 的文件大小不能外推到启用 LTO/strip 的 release 包。

## 兼容性与陷阱

按本次固定版本的[平台说明](https://github.com/indexable-inc/blaze/blob/v0.20261027.0/docs/platforms.md)，macOS 发布支持 Apple Silicon，Intel macOS 不支持；Windows MSVC 仍是手工验证的实验路径。
因此不能覆盖 remdia 当前 Windows x64、macOS arm64/x86_64 发布矩阵。
自带 nightly、优化后端和发布配置也需要分别验证，不能把开发编译收益直接等同于生产产物性能。

最初把源码副本也放在 `target/` 中时，曾出现构建退出成功但标记不更新的情况；这些增量数字已剔除。
将源码放到独立临时目录，构建产物通过 `CARGO_TARGET_DIR` 保留在 `target/blaze-eval/` 后，标记验证通过。
脚本采用此布局，并在错误或保护终止时保留失败状态。

## 复现

需要 macOS Apple Silicon、Python 3.9+、Git、GitHub CLI、现有 Rust/C/CMake 构建环境。
先在 remdia 根目录准备独立工具；不运行上游全局安装脚本：

```sh
mkdir -p target/blaze-eval/vendor target/blaze-eval/tool
gh release download v0.20261027.0 --repo indexable-inc/blaze \
  --pattern 'blaze-v0.20261027.0-aarch64-apple-darwin.tar.gz*' \
  --dir target/blaze-eval/vendor
cd target/blaze-eval/vendor
shasum -a 256 -c blaze-v0.20261027.0-aarch64-apple-darwin.tar.gz.sha256
cd ../../..
tar -xzf target/blaze-eval/vendor/blaze-v0.20261027.0-aarch64-apple-darwin.tar.gz \
  -C target/blaze-eval/tool
cargo fetch --locked
python3 scripts/benchmark-blaze.py \
  --blaze target/blaze-eval/tool/blaze-v0.20261027.0-aarch64-apple-darwin/blaze \
  --blaze-home target/blaze-eval/home \
  --output target/blaze-eval/reproduce-cli \
  --scope cli --jobs 1 --rounds 5
```

脚本自动准备独立 nightly、停止自己的旧 daemon，依次运行三组对照，并最终停止自己的 daemon。
每次必须使用新的 `--output`，防止把缓存命中误标为冷构建。
`--scope workspace --cold-only` 测全 SDK；`--scope native` 测插件并通过 C 导出函数的返回值验证修改。
`--variants blaze --profile release --cold-only` 可单测发布配置的兼容性。
输出含 `summary.json`、`environment.json`、每条命令的 `.json/.log/.time` 和各自 target；失败同样保留数据，并以非零状态退出。
源码临时副本的位置在 `summary.json` 的 `source_directory`，检查后可删除该目录。
所有二进制、下载包、缓存、日志和媒体输出均不提交 Git，仅提交汇总数据、脚本和报告。

混合构建的媒体检查可在正常 Cargo 插件已 stage 到 `dist/remdia/plugins` 后复现：

```sh
export REMDIA_PLUGIN_DIR="$PWD/dist/remdia/plugins"
mkdir -p target/blaze-eval/media-check
for variant in cargo-stable blaze; do
  cli="target/blaze-eval/reproduce-cli/$variant/target/debug/remdia"
  "$cli" probe "$PWD/tests/fixtures/av.mp4"
  "$cli" decode "$PWD/tests/fixtures/av.mp4" --software --frames 1000
  "$cli" thumbnail "$PWD/tests/fixtures/av.mp4" "target/blaze-eval/media-check/$variant.png" --at-us 1000000
  "$cli" extract "$PWD/tests/fixtures/av.mp4" "target/blaze-eval/media-check/$variant.wav" --duration-us 1000000
  "$cli" extract "$PWD/tests/fixtures/av.mp4" "target/blaze-eval/media-check/$variant.mp3" --duration-us 1000000
done
shasum -a 256 target/blaze-eval/media-check/*
```
